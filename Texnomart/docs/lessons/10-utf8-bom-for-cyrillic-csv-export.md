# 10. UTF-8 BOM в CSV-экспорте — чтобы Excel не сломал кириллицу

## Цель
Получить CSV-файл, который при двойном клике в Windows Excel отображает кириллицу корректно — без `Р‘РђР'`-крякозябр и без ручного выбора «Импорт из текста».

## Контекст / Проблема
В странице [`src/pages/Analytics.tsx`](../../src/pages/Analytics.tsx) пользователь может выгрузить отчёт в формате CSV (вторая радиокнопка в `GenerateReportDialog`). Утилита [`@/lib/utils/xlsxExport.ts`](../../src/lib/utils/xlsxExport.ts) формирует CSV через SheetJS:

```ts
const csv = XLSX.utils.sheet_to_csv(sheet);
const blob = new Blob([csv], { type: "text/csv;charset=utf-8" });
triggerDownload(blob, fileName);
```

На вид всё правильно: `charset=utf-8` в MIME, контент — нормальные UTF-8 байты. Но если этот CSV открыть двойным кликом в Windows Excel, столбцы «Клиент», «Статус», «Партнёр» превращаются в `РђР»РёС?РµСЂ Кар?РёРјРѕРІ`.

**Почему**: Excel под Windows игнорирует `Content-Type` (это HTTP-заголовок, а файл открывается из файловой системы) и **по умолчанию читает CSV в кодировке системы (CP1251 / Windows-1251)**, а не UTF-8. Без явного маркера он не понимает, что байты на самом деле UTF-8 — и поэтому кириллица перекодируется неправильно.

`charset` в MIME при создании Blob тоже здесь не работает: его читает только браузер для inline-просмотра, а Excel получает уже скачанный бинарный файл.

## Решение
**Префиксовать CSV-контент UTF-8 BOM (`﻿`)**. Этот невидимый маркер из трёх байт (`EF BB BF`) — стандартный для Excel сигнал: «дальше идёт UTF-8, читай соответственно».

```ts
const blob = new Blob(["﻿" + csv], {
  type: "text/csv;charset=utf-8",
});
```

В строковом виде BOM — это один code-unit `U+FEFF`. JavaScript-движок сериализует его в три UTF-8 байта при сборке Blob. На стороне получателя Excel видит этот префикс, переключается на UTF-8 — и кириллица отрисовывается корректно.

Для XLSX этот трюк не нужен — `.xlsx` — это zip с XML, кодировка декларируется внутри (`<?xml encoding="UTF-8"?>`), и BOM не имеет смысла. BOM прибавляется **только в CSV-ветке**.

## Принципы
- **Excel под Windows ≠ UTF-8 по умолчанию.** Любой CSV, который вы отдаёте конечному пользователю с кириллицей, обязан начинаться с BOM. Это работает для всех современных Excel (2007+), LibreOffice, Numbers, Google Sheets — никто не сломается от лишнего BOM
- **BOM добавляется на уровне Blob/строки, а не файла на диске.** Не надо ловить готовый File-объект и резать в него байты вручную — добавьте `"﻿"` к строке *перед* передачей в `new Blob([...])`
- **MIME `charset` — это про HTTP, не про двойной клик.** Чтобы CSV корректно открылся из локальной файловой системы, нужен внутрифайловый сигнал, а не HTTP-заголовок
- **Тестировать на той же ОС, что у пользователя.** Если разработчик сидит на macOS, проблемы он не увидит — `numbers.app` и macOS Excel умеют автоопределять UTF-8. Регрессии прилетят только от Windows-пользователей

## Чего не делать
- ❌ Полагаться на `Content-Type: text/csv; charset=utf-8` в `new Blob`. Для скачанного файла это не работает
- ❌ Конвертировать строку в Windows-1251 «чтобы Excel понял». Часть символов (узбекские диакритики, эмодзи) просто потеряется при перекодировке; UTF-8 + BOM покрывает всё
- ❌ Добавлять BOM в XLSX. Это бинарный формат с zip-обёрткой — BOM в начале сломает чтение
- ❌ Дублировать BOM. Если вы прокидываете CSV через несколько слоёв, проверьте, что BOM добавляется ровно один раз. Двойной BOM — отдельный набор крякозябр в первой ячейке
- ❌ Использовать `﻿` в коде через копипасту из браузера, где он может оказаться невидимым нулевым символом. Пишите явно строкой `"﻿"` или константой
